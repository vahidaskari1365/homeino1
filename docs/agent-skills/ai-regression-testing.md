# تست رگرشن AI هومینو (اقتباس از مهارت ai-regression-testing در ECC v2.2.1)

## مشکل اصلی

وقتی همان مدل AI که کد می‌نویسد بازبینی هم می‌کند، همان پیش‌فرض‌های غلط به هر دو مرحله
می‌آید: «نوشتم → خودم دیدم → درست به نظر رسید → باگ هنوز هست.» تنها پادزهر:
تست طلایی خودکار که assumptions را می‌شکند.

## کجاها در هومینو حیاتی است

| سطح | فایل | تست طلایی چه چیزی را قفل می‌کند |
|---|---|---|
| زنجیره LLM | `scripts/lib/llm-chain.mjs` | ترتیب fallback، پارس JSON، رفتار با کلید نامعتبر |
| ایجنت مجله | `scripts/magazine-daily.mjs` | سقف روزانه، dedupe (تکراری نگذاشتن)، ساختار بریف |
| ایجنت الهام | `scripts/inspiration-daily.mjs` | چرخش هوشمند (ترکیب استارو رد شود)، cap ۳۶۰، ساختار پین |
| درگاه AI | `src/app/api/ai/route.ts` | کاهش صادقانه: fail موتور → pollinations فقط تولید → mock با فلگ preview |
| Provider | `src/services/ai/provider.ts` | ترتیب رزولوشن gemini→zai→openai→freellm→mock |

## الگوهای تست (بدون شبکه، بدون کلید)

1. **قرارداد ثابت**: خروجی هر ایجنت schema ثابت دارد (`src/data/agent-runs` ساختار رسمی) — با fixture ورودی تست شود
2. **حالت‌های شکست**: شبیه‌سازی 429/۵۰۰/JSON خراب → باید fallback درست و summary فارسی درست
3. **بازگشت‌ناپذیری dedupe**: اجرای دوباره با همان ورودی → صفر آیتم جدید (تکرار ممنوع)
4. **مسیر کاهش**: بدون هیچ env کلیدی → `resolveProvider` باید mock بدهد و `editCapable=false`
5. **snapshot محتوایی**: تیتر بریف نباید خالی/انگلیسی/بیش از حد بلند باشد

## قانون اجرا

- هر باگ پیدا‌شده در ایجنت‌ها = اول تست طلایی که آن باگ را می‌گیرد، بعد فیکس
- تست‌ها با `npx vitest run` سبز بمانند — در CI هم اجرا می‌شوند
- fixtureها در `__fixtures__/` — هرگز در تست به API واقعی نزنیم
